01 Static-feature confound + overlapping "Frozen" terminology

The guide's §1 table lists "GRU-D Tuned (Primary Comparator)" — AUROC 0.9009 ± 0.0042 — as "Temporal vitals only (2-timestep, irregular)." §4.1's four-way model-definition table separately lists "Frozen GRU-D" (no "(Historical)" suffix) with the same "✓ temporal / ✗ static" characterization, described in §2.1 as reusing the existing GRU-D implementation with "HYPERPARAMETERS FROZEN: hidden dim = 32, dropout = 0.2, weight decay = 1e-4" — the identical configuration as "GRU-D Tuned."

The actual code (m2_ablations.py:120-145, GRUD.forward) shows this exact model is not temporal-only:

self.clf = nn.Sequential( nn.Linear(hid+stat, clf_hidden), nn.ReLU(), nn.Dropout(dropout), nn.Linear(clf_hidden, out) ) ... return self.clf(torch.cat([h, S], 1)) # h = temporal hidden state, S = 24 static features

stat=24 (static_cols, m2_ablations.py:58-68): age, gender, triage acuity, 9 utilization counts (ED/hosp/ICU visits at 30/90/365 days), 10 chief-complaint flags, med/med-reconciliation counts. This is baked into every saved AUROC for this model, including the 0.9009 figure.

This means Δ_static = AUROC_Hybrid − AUROC_Frozen would not cleanly answer "did adding static information help," since the comparator already has (a different, broader) static information fused in.

Three questions
  1. Should a genuinely temporal-only control (static_size=0, same architecture otherwise) be added as an additional ablation arm, so Δ_static has a clean denominator? (Recommendation, if useful: yes — it's a cheap addition given the architecture refactor is already needed for the two-branch design, and it makes the causal claim defensible under review.)
  2. In the guide's own usage, does "Frozen GRU-D" (§4.1) refer to the same checkpoint as "GRU-D Tuned" (§1), or something else?
  3. §10's final comparison table shows blank ("—") Coverage/Width cells for "GRU-D Tuned," even though this model's MAPIE/ECI coverage and width are already computed and saved (data/m2_multiseed_overall.csv: coverage_mapie 90.13%±0.16pp, width_mapie 0.2824±0.0586). Is that omission intentional, or should those cells be filled from the existing data?

02 Fusion width: 96-d vs. 64-d

§2's architecture diagram states the fusion layer is 64-d (temporal) + 32-d (static) = 96-d → Linear(96, 1). §6.1's hyperparameter table freezes the GRU-D hidden dim at 32 (matching the actual code's hid=32), which would make the real temporal embedding 32-d, not 64-d — so fusion would be 32+32=64-d → Linear(64, 1), not 96.

Question

Which is authoritative: retrain the temporal branch at hidden_dim=64 to match the diagram (a deviation from "frozen"/"already validated" hidden=32), or treat the diagram's 64-d/96-d labels as a documentation slip and build 32+32=64-d?

03 GRU-D learning rate: 5e-4 vs. 0.01

§6.1's table states: "Learning rate | 5e-4 | Already validated as best config in M2." Checked against every artifact that documents the tuning search: M2_Findings_Dossier.md §2's tuning stages vary pos_weight, hid, dropout, weight_decay, batch_size, early_stopping — no learning-rate sweep appears anywhere; data/m2_grud_tuning_trace.csv's header has no learning-rate column; and the actual tuned/frozen model's code (m2_ablations.py:158-165, SKLearnGRUD.__init__) hardcodes lr=0.01 as the default, with its own inline comment naming only hid=32, dropout=0.2, weight_decay=1e-4 as "the winning config" — lr is not part of that list.

Question

Should the frozen temporal branch train at lr=0.01 (what's actually in every saved artifact), or at 5e-4 (the guide's stated value, which would need its own validation since it was never tested in any saved trace)?

04 Stale "Historical" baseline number

§1/§10 state: "GRU-D Frozen (Historical) | ... | 0.8937 ± 0.0128 | 0.4196 ± 0.0424 | ... pre-tuning baseline", with §1's instruction "Do not rerun, recompute, or modify."

This number predates a fit/calibration-split leakage fix documented in M2_Findings_Dossier.md §1.2 (10,156 overlapping patients found at seed 42 under the old row-level split). The pre-tuning baseline was re-run after that fix, and the currently-archived, reproducible result (data/m2_seed_results_pretuning/seed_{42,123,7,456,789}.json, aggregated in data/m2_multiseed_overall_pretuning.csv) is 0.8925 ± 0.0136 (AUPRC 0.4176 ± 0.0469) — not 0.8937/0.0128 or 0.4196/0.0424. No file in the repo currently reproduces the guide's exact stated figures.

Question

Should the Historical row report the reproducible 0.8925 ± 0.0136 (with a note that the guide's figure predates the leakage fix), or the guide's stated 0.8937 ± 0.0128 (footnoted as supervisor-provided, not independently reproducible from current repo artifacts)? This doesn't affect anything else — §0.1's Fix #1 already relegates this specific number to a historical footnote regardless of which value is used.
